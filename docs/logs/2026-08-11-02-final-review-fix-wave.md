# 2026-08-11-02: Final whole-branch review fix wave for the one-shot shell

**Status:** Implemented

## Context

`feat/one-shot-capture-shell` replaced the test-harness UI with a one-shot product shell
over 17 commits, each reviewed on its own. A final review of the whole branch found
defects that no per-task review could see, because each one is an interaction between
commits: state written by one screen and read by another, copy duplicated across two
types added weeks apart, documentation describing an app that three commits later no
longer existed.

Two of them are user-visible on the screen a failed capture navigates to *automatically*:

1. A capture that failed to assemble was silently relabelled `.processing` by any later,
   unrelated import — and nothing ever re-assembled it. `ResultView` derives what it
   shows from that phase, so opening the capture showed "Putting it together…" forever:
   no image, no export bar, no error, and no exit but backgrounding the app.
2. `StitchKit`'s errors are plain `Error` enums with no `LocalizedError` conformance, so
   `error.localizedDescription` — stored in `Capture.Phase.failed` and printed by
   `CaptureFailureView` — read *"The operation couldn't be completed.
   (StitchKit.Compositor.CompositorError error 1.)"*.

## Options

### Where to fix the stranded-capture bug

| Approach | Pros | Cons |
|---|---|---|
| Make `ResultView` distinguish "actually assembling" from "abandoned" | No model change | Treats the symptom; every future reader of `phase` inherits the same lie, and the model would still hold a state that means two different things |
| Stop `reload()` rewriting phases (chosen) | The state stops lying at its source; one line | Changes when a failed capture is retried, so the retry has to be re-established deliberately |
| Re-assemble every non-ready capture from `runImport` too | Also self-heals | Turns one import into N composites of unrelated captures; the user asked for one |

### Where to translate errors

| Approach | Pros | Cons |
|---|---|---|
| Conform `StitchKit`'s errors to `LocalizedError` | Fixes it for every caller | `StitchKit` is the finished core and is off-limits; it would also put product copy in a pure pixel library |
| Map at each call site | Local | Four call sites, four chances to drift — exactly the duplication `CaptureCondition` exists to prevent |
| `CaptureCondition.message(for:)` (chosen) | One translation, next to the only other pipeline→English translation, table-testable | The app must know the pipeline's error cases by name |

### What to do with an error we have no wording for

| Approach | Pros | Cons |
|---|---|---|
| Always show a generic sentence | Never leaks a type name | Throws away real messages ("the file doesn't exist", "the disk is full") that are strictly better than anything generic |
| Always pass through `localizedDescription` | Keeps real messages | Puts the bridged placeholder back on screen — the original bug |
| Pass through unless the description is the placeholder (chosen) | Keeps real messages, blocks the placeholder | Needs a discriminator for "this description is meaningless" |

## Decision

Fix the stranded capture at its source (`reload()` never rewrites a phase), translate every
user-visible error through a single `CaptureCondition.message(for:)`, and detect a
meaningless bridged description by the fact that it interpolates its own error domain.

## Rationale

`reload()`'s demotion had exactly one real effect — turning `.failed` into `.processing` —
because `.ready` was already preserved and `.processing` was already `.processing`. That
made it pure damage: it destroyed the only record that a capture had failed, in a method
whose job is to reconcile disk with memory. Retrying is still wanted, so
`performRefresh` now re-assembles anything not `.ready` that has no proxy; the retry moved
to the place that actually does the work.

The placeholder discriminator matters because "unknown error" is not one population. A
bridged Swift error and an `NSCocoaErrorDomain` file error are both unrecognised, and the
right answer differs. The bridged placeholder is generated by interpolating the domain
(the Swift type's own name) into a fixed template, in every locale — so
`description.contains(error.domain)` identifies it without pattern-matching English.

## What Changed

- `Seamly/Seamly/Core/CaptureModel.swift` — `reload()` preserves phases; `performRefresh`
  assembles oldest-first (newest arrival wins `pendingResult`) and re-assembles anything
  not `.ready`; every user-visible error goes through `CaptureCondition.message(for:)`
  while `Diagnostics` gains the raw error; `Capture` loses `flaggedSeamCount`,
  `unresolvedChromeCount`, `isIncomplete`, and its "in the Library" doc comment.
- `Seamly/Seamly/DesignSystem/CaptureCondition.swift` — new `message(for:)` plus its
  unrecognised-error fallback.
- `Seamly/Seamly/DesignSystem/ConditionNotice.swift` — dead `.nothingToStitch`/`.failed`
  rows deleted; owns its own insets so a clean capture gets no empty strip.
- `Seamly/Seamly/Features/Result/ResultView.swift` — unreachable `.nothingToStitch` arm
  removed; export errors translated.
- `Seamly/Seamly/Features/Capture/{Photo,Video}ImportButton.swift` — vestigial
  `onStarted:` removed (its only caller, `CaptureStartView`, was deleted); errors
  translated.
- `Seamly/SeamlyTests/{CaptureConditionTests,CaptureModelRegressionTests}.swift` — five
  new tests; one existing test's premise and one false comment corrected.
- `Seamly/SeamlyUITests/SeamlyUITests.swift` — onboarding genuinely dismissed;
  assertions moved from `exists` to `isHittable`.
- `README.md`, `CLAUDE.md` — describe the shell that exists.

## What Was Discovered

- **A test asserted the bug.** `arrivalAssemblyReportsBusyOnlyForGenuineWorkNotAStrayFailedCapture`
  required the failed capture to have been demoted to `.processing` — it was written to
  pin a *different* fix (the busy signal) and adopted the demotion as scenery. Fixing the
  real defect broke it. Its premise moved to the second, still-unassembled capture.
- **That same test's timing comment was false.** It claimed the seeded capture was
  "deliberately large, so its composite takes long enough to reliably observe" — but the
  seeded session has no seams, so `Compositor.refineSeams` maps over nothing and takes the
  cheap path. What makes the flag observable is that `assemble` raises the counter
  synchronously, before its first suspension point.
- **A UI test passed with a sheet over the screen.** `testHomeShowsRecordFirst` waited on
  "Get Started", which `OnboardingView` only shows on its last page, so its dismissal
  block never ran — and sheet-covered elements still satisfy `exists`. It was proven to
  discriminate by breaking `HomeView`'s headline (fails at the home assertion) and by
  removing the dismissal (fails at the new hittability assertion). Both reverted.
- **Deleting a dead enum case costs exhaustiveness.** `ResultView` cannot say "the
  remaining two cases" in Swift, so removing the unreachable `.nothingToStitch` arm meant
  taking `default` — a real, if small, loss of compiler help, accepted over keeping a
  branch that claims to be reachable.
- **Not everything unreferenced is dead.** `Capture.orderAssumed` has no app-side reader
  but is asserted by `MediaImportTests`; it stays.

## Second pass — running the app

Everything above passed 42 unit tests, 4 UI tests, ten task reviews and a whole-branch
review. Then someone launched the app and looked at it, which had never happened, and
found a defect none of that could catch.

**In dark mode the record button was nearly invisible** — the hero action of a
record-first app, rendering as a dark smudge on black. `RPSystemBroadcastPickerView`
draws a fixed black glyph in *both* appearances; it does not adapt. The backing
`Circle().fill(.tint.opacity(0.15))` was near-black in dark mode, so the glyph had
nothing to sit against. Light mode looked fine, which is why nobody suspected it.

Restyling the picker's own glyph was rejected again for the reason
`BroadcastPickerButton` already documents: reaching into its private subviews is fragile
across iOS versions. So the backing carries the contrast instead — a solid `.tint` disc,
which reads in both appearances. Verified by screenshot in each, not by reasoning.

**Zoom was fixed rather than deferred.** `.scaleEffect` is a render-time transform: the
view's *measured* size stays at 1×, so the scroll view's content extent never grows and
magnified detail sits outside every reachable offset. `CaptureCanvas` now computes a
layout size (`viewport width × zoom`, times the proxy's aspect ratio) and applies it with
`.frame`, so the extent grows with the zoom. `ZoomState`'s accumulation and 1×–6× clamp
are unchanged — they were always correct.

The accessibility hint said "Double-tap to fit", but double-tap calls `reset()`, which
returns to 1× — and at 1× a long screenshot is still far taller than the screen. The
words were made true rather than vaguer: "Double-tap to zoom back out."

**`testExample` was deleted.** XCTest runs methods alphabetically, so the Xcode template
stub — which asserted nothing — launched the app before `testHomeShowsRecordFirst` and
let `HomeView.task` set `hasSeenOnboarding`. Onboarding was therefore never on screen for
the one test whose job is to walk through and dismiss it. The dismissal fix recorded above
was real, but in a full-suite run it was never exercised, and its deliberate-break
evidence would not have reproduced.

Also closed from the re-review: `ResultView` regained exhaustiveness by naming
`.clean, .imperfect` and genuinely handling `.nothingToStitch` with the view that already
exists for it, rather than `default:`. And `fullComposite`/`exportPDF` now log the raw
error alongside the bridged string — the mapping work had left `Diagnostics`, the only
window into a device failure, recording the placeholder while the *user* got the good
sentence. Backwards.

## Follow-ups

- **Nothing has driven the app past its home screen.** This environment has no tap
  capability, so the zoom fix is verified by construction and by build, not by pinching a
  real stitch and scrolling to a join. That check is still owed.
- UI-test seeding still has no launch-argument plumbing, so the UI tests only cover the
  no-captures branch of home. Deferred rather than adding test-only hooks to production.
- A permanently-failing capture is re-composited on every foreground, silently. Recoverable
  by deleting it; consider skipping the retry unless the manifest's mtime changed.
- JPEG is still listed as an export format in `README.md` and `CLAUDE.md`, but
  `Exporter.jpegURL` has no caller in the shell.
